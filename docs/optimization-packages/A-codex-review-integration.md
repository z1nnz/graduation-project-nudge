# A 包：既有 PR 審查與整合

負責：Codex。對應原第 1 項。先讀 [共同規則](README.md)。

## 目的

把「提交 PR」「CI 綠燈」「能實際使用」分開判斷。保留組員已完成的工作，避免重寫，同時不把有依賴、權限漏洞或未經驗證的資料修改直接合併。

## A1：產生 PR 依賴清單

逐 PR 記錄：head SHA、base、改動範圍、需求來源、前置 PR、衝突、最新 CI、人工檢查、是否含 migration，以及建議處置。

```sh
gh pr list --state open --limit 50
gh pr view PR_NUMBER --json number,title,baseRefName,headRefOid,isDraft,statusCheckRollup
gh pr diff PR_NUMBER
```

文字自評與分數不是驗收證據；文件 PR 要確認指令、路徑與下載交付真的可用。

## A2：審查範圍

- 需求軸：是否符合來源規格、是否漏掉錯誤情境、是否擴大範圍。
- 程式軸：共用契約、帳號切換、撤回同意、重試、重複獎勵、資源清理與維護性。
- UI 軸：主要流程、空資料、錯誤、窄螢幕、角色差異。
- 韌體軸：型號、依賴版本、展示標示、畫面、建置與實機限制。不用編譯成功推論接線／面板正常。

有阻擋問題則提出具體行為、檔案與重現方式，修正後檢查新 head；不以管理員 bypass 取代修正。若只是核准規則阻擋，亦須先確認其餘 gate、差異與相依已滿足，再依已授權範圍處理。

## A3：跨包介面協調

若 C／D 需要 AppState 或 `app.js` 的新介面，先檢查既有能力是否足夠；不足時以最小獨立變更提供。

介面必須說明：資料來源、目前使用者／relationship scope、loading／cache／error、帳號或關係切換的失效方式。不得替所有使用者預設啟用分享。

## A4：整合驗收

- 角色：後台完整鏈 → 初始角色商城 → 購買／裝備 → 圖鑑 → 合法進化。
- 個人：未完成任務 → 自主行動 → pending → Cloud 確認 → 角色回應。
- 家庭：綁定 → 孩子同意 → 家長只見同意摘要 → 撤回後不可繼續讀取。
- 團體：邀請 → 接受 → 成員參與 → 管理者彙總；移除成員後舊介面不能繼續讀取。
- 房間：成員自行開始／結束；房主不能控制別人活動。
- 切換：帳號／家庭／團體切換後不能短暫顯示前一個人的資料。

真實帳號測試缺少合法測試帳號或權限時，記錄缺口，不自行取得他人憑證，也不把 emulator 結果寫成 production 驗收。

## 交付與完成條件

交付 `docs/acceptance/` 下的逐 PR 決策及整合證據。每筆標示 examined SHA、檢查日期、通過／待修／被依賴阻擋。分批安全合併，不要求一次全合併。

A 完成是既有 PR 均有明確處置、可合併部分經驗證整合，以及 B／C／D 的整合結果與限制可追溯；不是只整理一張清單。
